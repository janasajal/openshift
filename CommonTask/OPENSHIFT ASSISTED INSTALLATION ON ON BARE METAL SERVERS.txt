OBJECTIVE
---------
A production OpenShift cluster was installed on 10 bare metal servers using
the Assisted Installer method. The environment included IBM SAN storage,
HAProxy with Keepalived floating VIPs for API and Ingress load balancing,
a bastion server for orchestration, and an internal DNS server. Post-install
IBM Block CSI driver integration was configured for dynamic storage provisioning.

--------------------------------------------------------------------------------
PHASE 1 — INFRASTRUCTURE PLANNING & NODE LAYOUT
--------------------------------------------------------------------------------

Node role assignments were planned before any server was touched. The layout
below was finalized based on minimum hardware requirements and HA considerations.

  Cluster Node Layout:
  -----------------------------------------------------------------------
  Role              Count   Servers
  ----------------  ------  -----------------------------------------------
  Bootstrap         1       bm-node-01 (temporary — removed after install)
  Control Plane     3       bm-node-02, bm-node-03, bm-node-04
  Worker            6       bm-node-05, bm-node-06, bm-node-07,
                            bm-node-08, bm-node-09, bm-node-10
  HAProxy + VIP     2       haproxy-01 (MASTER), haproxy-02 (BACKUP)
  Bastion           1       bastion.company.com
  -----------------------------------------------------------------------

  Minimum hardware specifications confirmed per role:

  Control Plane Nodes (x3):
    CPU    : 16 vCPU
    RAM    : 32 GB
    DISK   : 120 GB (local OS)
    NIC    : 2 x 10GbE (bonded)

  Worker Nodes (x6):
    CPU    : 16 vCPU
    RAM    : 64 GB
    DISK   : 120 GB (local OS)
    NIC    : 2 x 10GbE (bonded)
    SAN    : IBM SAN LUNs mapped via FC

  Network VLAN layout confirmed:
    Management VLAN : 10.10.10.0/24  (iDRAC/BMC access)
    Cluster VLAN    : 192.168.10.0/24 (OpenShift node communication)

ISO was generated. DNS is a hard prerequisite — incorrect DNS records cause
cluster bootstrap to fail.

  api.ocp.company.com              IN A   192.168.10.100

PHASE 3 — HAPROXY LOAD BALANCER CONFIGURATION
--------------------------------------------------------------------------------

HAProxy was configured on both haproxy-01 and haproxy-02 to load balance
four critical ports: API (6443), Machine Config Server (22623), HTTP (80),
and HTTPS (443).

  /etc/haproxy/haproxy.cfg applied on both HAProxy nodes:
  -----------------------------------------------------------------------
  global
      log         127.0.0.1 local2
      chroot      /var/lib/haproxy
      maxconn     4096
      daemon

  defaults
      mode                    tcp
      log                     global
      option                  tcplog
      retries                 3
      timeout connect         10s
      timeout client          1m
      timeout server          1m

  # API Server — port 6443
  frontend openshift_api_frontend
      bind *:6443
      default_backend openshift_api_backend
      mode tcp

  backend openshift_api_backend
      mode tcp
      balance roundrobin
      server master-0 192.168.10.10:6443 check
      server master-1 192.168.10.11:6443 check
      server master-2 192.168.10.12:6443 check

  # Machine Config Server — port 22623 (bootstrap phase)
  frontend machine_config_frontend
      bind *:22623
      default_backend machine_config_backend
      mode tcp

  backend machine_config_backend
      mode tcp
      balance roundrobin
      server master-0 192.168.10.10:22623 check
      server master-1 192.168.10.11:22623 check
      server master-2 192.168.10.12:22623 check

  # Ingress HTTP — port 80
  frontend openshift_http_frontend
      bind *:80
      default_backend openshift_http_backend
      mode tcp

  backend openshift_http_backend
      mode tcp
      balance roundrobin
      server worker-0 192.168.10.20:80 check
      server worker-1 192.168.10.21:80 check
      server worker-2 192.168.10.22:80 check
      server worker-3 192.168.10.23:80 check
      server worker-4 192.168.10.24:80 check
      server worker-5 192.168.10.25:80 check

  # Ingress HTTPS — port 443
  frontend openshift_https_frontend
      bind *:443
      default_backend openshift_https_backend
      mode tcp

  backend openshift_https_backend
      mode tcp
      balance roundrobin
      server worker-0 192.168.10.20:443 check
      server worker-1 192.168.10.21:443 check
      server worker-2 192.168.10.22:443 check
      server worker-3 192.168.10.23:443 check
      server worker-4 192.168.10.24:443 check
      server worker-5 192.168.10.25:443 check
  -----------------------------------------------------------------------

  Command used:
  $ systemctl enable haproxy --now

  Output observed:
  ● haproxy.service - HAProxy Load Balancer
     Active: active (running) since Mon 2026-05-19 08:00:00 IST

PHASE 4 — KEEPALIVED VIP CONFIGURATION
--------------------------------------------------------------------------------

Keepalived was configured to manage two floating VIPs — one for API access
and one for Ingress. haproxy-01 was set as MASTER and haproxy-02 as BACKUP.
The VIP floats automatically to haproxy-02 if haproxy-01 or its HAProxy
process fails.

  /etc/keepalived/keepalived.conf on haproxy-01 (MASTER):
  -----------------------------------------------------------------------
  vrrp_script chk_haproxy {
      script "killall -0 haproxy"
      interval 2
      weight 2
  }

  vrrp_instance API_VIP {
      state MASTER
      interface bond0
      virtual_router_id 51
      priority 101
      advert_int 1
      authentication {
          auth_type PASS
          auth_pass ocp-secret-2026
      }
      virtual_ipaddress {
          192.168.10.100/24
      }
      track_script {
          chk_haproxy
      }
  }

  vrrp_instance INGRESS_VIP {
      state MASTER
      interface bond0
      virtual_router_id 52
      priority 101
      advert_int 1
      authentication {
          auth_type PASS
          auth_pass ocp-secret-2026
      }
      virtual_ipaddress {
          192.168.10.101/24
      }
      track_script {
          chk_haproxy
      }
  }
  -----------------------------------------------------------------------

  On haproxy-02 (BACKUP) the same configuration was applied with:
      state   BACKUP
      priority 99

  Command used:
  $ systemctl enable keepalived --now

  VIP assignment was verified on haproxy-01:

  Command used:
  $ ip addr show bond0 | grep 192.168.10.10

  Output observed:
  inet 192.168.10.100/24 scope global secondary bond0
  inet 192.168.10.101/24 scope global secondary bond0

  Observation:
  Both VIPs were confirmed active on haproxy-01. On a simulated failure
  of haproxy-01, keepalived on haproxy-02 picked up both VIPs within
  2 seconds (advert_int value).

PHASE 6 — DISCOVERY ISO GENERATION VIA ASSISTED INSTALLER API
--------------------------------------------------------------------------------

The cluster configuration was submitted to the Assisted Installer API from
the bastion server and a discovery ISO was generated for node booting.

  Environment variables were set on bastion:

  $ export AI_URL="https://api.openshift.com/api/assisted-install/v2"
  $ export CLUSTER_NAME="ocp-prod"
  $ export BASE_DOMAIN="company.com"
  $ export OCP_VERSION="4.14.15"

  Cluster was created via API:

  Command used:
  $ curl -s -X POST "$AI_URL/clusters" \
      -H "Content-Type: application/json" \
      -H "Authorization: Bearer $(cat /root/ai-token)" \
      -d '{
        "name": "ocp-prod",
        "openshift_version": "4.14.15",
        "base_dns_domain": "company.com",
        "pull_secret": '<pull_secret>',
        "high_availability_mode": "Full",
        "api_vip": "192.168.10.100",
        "ingress_vip": "192.168.10.101",
        "ssh_public_key": "<bastion_pub_key>"
      }' | python3 -m json.tool

  Output observed:
  {
    "id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
    "name": "ocp-prod",
    "status": "pending-for-input",
    "openshift_version": "4.14.15",
    "api_vip": "192.168.10.100",
    "ingress_vip": "192.168.10.101"
  }

  Discovery ISO was generated:

  Command used:
  $ curl -s -X POST "$AI_URL/infra-envs" \
      -H "Content-Type: application/json" \
      -H "Authorization: Bearer $(cat /root/ai-token)" \
      -d '{
        "name": "ocp-prod-infra",
        "cluster_id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
        "openshift_version": "4.14.15",
        "pull_secret": '<pull_secret>',
        "image_type": "full-iso",
        "proxy": {
          "no_proxy": "192.168.10.0/24,.company.com"
        }
      }' | python3 -m json.tool

  Output observed:
  {
    "id": "infra-env-xyz789",
    "download_url": "https://api.openshift.com/api/assisted-install/v2/infra-envs/infra-env-xyz789/downloads/image",
    "type": "full-iso",
    "expires_at": "2026-05-26T08:00:00Z"
  }

  ISO was downloaded to the bastion web server directory:

  Command used:
  $ curl -L -o /var/www/html/discovery.iso \
      "https://api.openshift.com/api/.../downloads/image" \
      -H "Authorization: Bearer $(cat /root/ai-token)"

  $ ls -lh /var/www/html/discovery.iso

  Output observed:
  -rw-r--r--. 1 root root 1.1G May 19 08:30 discovery.iso

  Observation:
  The ISO was hosted via the bastion HTTP server so it could be mounted
  via iDRAC virtual media on each bare metal node without transferring
  the file to each server individually.

PHASE 7 — BARE METAL NODE BOOT WITH DISCOVERY ISO
--------------------------------------------------------------------------------

The discovery ISO was mounted on each bare metal server via iDRAC virtual
media and each server was set for one-time boot from the virtual CD-ROM.

  Command used (Dell iDRAC via racadm — repeated per node):

  $ racadm -r idrac-bm-node-02.company.com \
             -u root -p password \
             remoteimage -c -l http://bastion.company.com/discovery.iso

  $ racadm -r idrac-bm-node-02.company.com \
             -u root -p password \
             set iDRAC.ServerBoot.BootOnce Enabled

  $ racadm -r idrac-bm-node-02.company.com \
             -u root -p password \
             set iDRAC.ServerBoot.FirstBootDevice VCD-DVD

  $ racadm -r idrac-bm-node-02.company.com \

PHASE 11 — IBM BLOCK CSI DRIVER INSTALLATION
--------------------------------------------------------------------------------

The IBM Block CSI operator was installed from OperatorHub and configured
to enable dynamic PV provisioning from IBM SAN storage.

  Operator subscription was created:

  Configuration applied:
  -----------------------------------------------------------------------
  apiVersion: operators.coreos.com/v1alpha1
  kind: Subscription
  metadata:
    name: ibm-block-csi-operator
    namespace: openshift-operators
  spec:
    channel: stable
    name: ibm-block-csi-operator
    source: certified-operators
    sourceNamespace: openshift-marketplace
  -----------------------------------------------------------------------

  The IBMBlockCSI instance was created:

  -----------------------------------------------------------------------
  apiVersion: csi.ibm.com/v1
  kind: IBMBlockCSI
  metadata:
    name: ibm-block-csi
    namespace: openshift-operators
  spec:
    controller:
      repository: cp.icr.io/cp/spectrum/scale/csi/ibm-block-csi-driver-controller
      tag: 1.11.0
    node:
      repository: cp.icr.io/cp/spectrum/scale/csi/ibm-block-csi-driver-node
      tag: 1.11.0
  -----------------------------------------------------------------------

  A StorageClass was created for IBM SAN dynamic provisioning:

  -----------------------------------------------------------------------
  apiVersion: storage.k8s.io/v1
  kind: StorageClass
  metadata:
    name: ibm-block-gold
    annotations:
      storageclass.kubernetes.io/is-default-class: "true"
  provisioner: block.csi.ibm.com
  parameters:
    SpaceEfficiency: deduplicated
    pool: ocp-pool
    csi.storage.k8s.io/provisioner-secret-name: ibm-storage-secret
    csi.storage.k8s.io/provisioner-secret-namespace: openshift-operators
  reclaimPolicy: Retain
  allowVolumeExpansion: true
  volumeBindingMode: Immediate
  -----------------------------------------------------------------------

  CSI pod health was verified:

  Command used:

  Key lessons observed during this lab:
  1. DNS must be 100% correct before ISO generation — incorrect SRV records
     cause bootstrap etcd to fail silently.
  2. HAProxy must be listening on port 22623 during bootstrap — this port
     is only needed during install and can be restricted post-install.
  3. IBM SAN multipath must be active on nodes before the CSI driver is
     installed — the driver probes existing paths at startup.
  4. Keepalived advert_int should match across both nodes — mismatched
     values cause VIP flapping.
